API Reference

OptiFlowz API Reference

Complete Express API reference for authentication, video delivery, playlists, quizzes, moderation, analytics, reports, and user-facing platform features.

The OptiFlowz backend exposes REST endpoints for a video platform built around users, video assets, watch progress, playlists, comments, people, quiz attempts, certificates, and analytics.

Use the cards below to open a focused route group. Endpoints marked as protected require a Bearer JWT token, while moderation endpoints require an admin or uploader role.

Endpoints

Auth

Register, login, OAuth, profile updates, password reset, and profile images.

Videos

Search, playback details, upload initiation, progress, reactions, history, and recommendations.

Video Moderation

Video metadata, thumbnails, subtitles, Mux track management, and generated details.

Playlists

Playlist search, featured lists, saved playlists, and playlist video browsing.

Quizzes

Quiz management, questions, access rules, attempts, answers, certificates, and scoring.

People

Speaker and chair profiles, search, sorting, profile images, and admin maintenance.

Comments

Comment posting, replies, editing, deletion, and reactions.

Channels

Channel details, published videos, and public playlist collections.

Analytics

Video and channel performance, audience, geography, engagement, and time-series metrics.

Reports

PDF analytics export for video platform reporting.

General rules

  • The local backend base URL is http://localhost:4000.
  • JSON routes use the header Content-Type: application/json.
  • Protected routes use the header Authorization: Bearer <jwt-token>.
  • Routes marked as Admin require a user with the role admin or uploader.
  • Routes marked as Optional also work without a token, but return personalized data when a token is provided.
  • Upload routes use multipart/form-data, usually the field file.

Auth /api/auth

POST/api/auth/registerPublic

Registers a new user and returns a JWT token.

Body

{
  "email": "user@example.com",
  "password": "password123",
  "full_name": "Full Name",
  "description": "",
  "eaes_member": false
}

Validation

Email must be valid, password must be at least 8 characters, and full name is required.

Response

{
  "user": { "email": "...", "role": "user" },
  "token": "jwt"
}
POST/api/auth/loginPublic

Logs a user in with email and password.

Body

{
  "email": "user@example.com",
  "password": "password123"
}

Note

The password is verified against a bcrypt hash.

Response

{
  "user": { "email": "...", "role": "user" },
  "token": "jwt"
}
POST/api/auth/passwordResetRequestPublic

Generates a password reset token and sends it through the external n8n webhook.

Body

{ "email": "user@example.com" }

Limit

This route is rate-limited to prevent abuse.

Response

{
  "message": "If that email is registered..."
}
POST/api/auth/passwordReset/verifyPublic

Checks whether the reset token is valid and not expired.

Body

{
  "email": "user@example.com",
  "token": "ABC123"
}

Validation

The token is a short code, and email must be valid.

Response

{ "valid": true }
POST/api/auth/passwordResetPublic

Changes the password when the reset token is valid.

Body

{
  "email": "user@example.com",
  "token": "ABC123",
  "newPassword": "newPassword123"
}

Effect

The new password is hashed and the token is marked as used.

Response

{ "message": "Password reset successful" }

Backend Architecture

How requests move through the Express application and where each backend responsibility lives.

Request lifecycle

The API has a thin application bootstrap and a central route registry. Cross-cutting middleware runs before requests enter a domain module.

1

Application bootstrap

src/server.js loads the environment, creates the Express app, starts the HTTP server, and initializes database role logging.

2

Global middleware

src/app.js enables trusted proxy headers, CORS, conditional JSON parsing, and a dedicated raw-body parser for the Mux webhook.

3

Route registration

src/routes/index.js mounts every domain router below /api and exposes the root /health check.

4

Domain handling

Route middleware applies authentication and roles before controllers, handlers, and services validate input, enforce ownership, query PostgreSQL, or call external integrations.

5

Response and errors

Handlers return JSON or binary output. Unmatched routes and unhandled errors fall through centralized 404 and 500 middleware.

Module boundaries

The backend is organized by domain, with shared infrastructure kept outside business modules.

Domain modules

auth, videos, playlists, people, comments, channels, quizzes, analytics, and reports.

Cross-cutting code

config, database, middleware, and common hold environment, DB pools, request processing, ownership checks, validation, logging, and response helpers.

Read/write separation

Queries use explicit readPool and writePool connections. Production reads can be routed to a regional replica while writes remain on the leader.

Service integrations

Mux handles video delivery, R2 stores uploaded images, n8n supports automation workflows, MaxMind resolves geography, and Puppeteer renders PDF reports and certificates.

Bearer token flow

1

Issue

Login, registration, or Google OAuth returns a signed JWT together with the user profile.

2

Send

The client places the token in Authorization: Bearer <jwt-token> on protected requests.

3

Verify

jsonwebtoken verifies the signature with JWT_SECRET and attaches the payload to req.user.

4

Authorize

Role middleware and ownership helpers decide whether the authenticated subject can access the requested resource.

Security controls

Password handling

Passwords are hashed before storage. Reset request, verification, and reset endpoints use dedicated rate limiters.

Ownership checks

Video analytics verifies that the current uploader owns the video. Quiz and comment mutations similarly validate creator or user ownership.

Upload validation

Multer-based upload middleware limits accepted file types and sizes before images or subtitle files reach service logic.

Webhook trust

Mux is not authenticated with JWT. Its raw request body is validated with the Mux-Signature HMAC before JSON is processed.

Media Pipeline

The complete path from an admin initiating a video upload to ready playback and later moderation.

Upload to playback

Large media files travel directly from the client to Mux; the API coordinates metadata and lifecycle state.

1

Initiate upload

POST /api/videos/upload/initiate creates the video record and asks Mux for a direct upload URL. The request requires an admin or uploader token.

2

Direct client transfer

The browser uploads the media to the returned Mux URL. Mux receives the database video ID through passthrough metadata and can generate the requested subtitle track.

3

Signed webhook

Mux posts asset events to /api/videos/webhook/mux. The backend keeps the body raw until its HMAC signature is verified.

4

Asset synchronization

A ready event stores duration, asset ID, playback ID, status, and a default thumbnail URL. Error and deletion events update or remove the matching record.

5

Playback delivery

Public ready videos expose Mux playback metadata to discovery and detail endpoints. Private videos remain limited to their uploader.

6

Post-upload moderation

Admins can update metadata, upload a thumbnail, replace or generate subtitles, generate chapters, preview generated details, and request asset deletion.

Supporting services

Mux Video

Direct uploads, adaptive playback, asset state, generated subtitles, text tracks, and default video thumbnails.

Mux AI

@mux/ai generates chapters from an existing Mux asset and a requested language, using the configured OpenAI provider.

Cloudflare R2

An S3-compatible client stores uploaded profile, person, video, and playlist imagery outside PostgreSQL.

n8n workflows

Automation webhooks support password-reset delivery and AI-assisted subtitle or metadata generation workflows.

Webhook parsing is intentionally different

The Mux endpoint receives application/json as raw bytes, while regular JSON routes use the normal Express JSON parser. This preserves the exact payload needed for signature verification.

Analytics & Tracking

How view sessions, watch time, audience dimensions, engagement, and reports are derived.

Playback tracking flow

1

Start or reuse a view

Opening a video creates a video_views session or reuses a matching session created within the previous two hours, avoiding duplicate view-count increments.

2

Identify the viewer

Authenticated sessions use the user ID. Anonymous sessions use an HMAC-hashed IP plus user agent; raw IP is used only for the location lookup before hashing.

3

Enrich dimensions

Country, ISO country code, city, and user agent are stored with the view so geographic, device, and operating-system breakdowns can be calculated.

4

Accumulate watch time

POST /api/videos/heartbeat accepts sequential heartbeat numbers and only counts playing time. Each delta is capped to protect totals from delayed or duplicated requests.

5

Update user progress

For authenticated viewers, counted heartbeat time is also accumulated in watch_progress for history, continue watching, recommendations, and quiz requirements.

Available metrics

Performance

Total and first-time views, total watch time, average watch time per viewer, likes, dislikes, and comments.

Audience

Device split, operating-system split, and a country/city geographic breakdown derived from captured view dimensions.

Retention

Completion buckets group viewers below 25%, through intermediate ranges, and above 95% completion.

Engagement

Video engagement compares accumulated watch time with video duration. Channel analytics also returns average engagement per uploaded video.
